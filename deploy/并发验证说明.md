# 2000人在考优化与验证

更新：2026-10-08。2000人在考是目标容量，不能只凭本地测试承诺任意服务器可承载。

## 2026-10-11～12 补充实测

本轮已增加真实 MySQL、密码登录与 2000 个异步读取请求的突发场景。H2 基线通过，但 MySQL 多轮保存答案出现死锁并返回 HTTP 500，集中读取也出现连接错误，当前不能认定已通过 2000 人稳定容量验收。

`ExamHttpLoadTest` 新增显式参数：

- `-Dhnexam.loadtest.login=true`：计入 2000 个真实密码登录，最多 20 个同时执行。
- `-Dhnexam.loadtest.mysql=true`：只使用写死的本机隔离库 `hn_exam_loadtest_20261011` 和专用账号 `hn_loadtest_20261011`；账号仅有该库权限，密码从 `HNEXAM_LOADTEST_PASSWORD` 环境变量读取。运行前须单独准备此测试库及专用账号，不能赋予业务库权限。测试会对隔离库执行 create-drop。
- `-Dhnexam.loadtest.burst=true`：集中发起 2000 个异步答卷读取请求；不代表 2000 个浏览器或 2000 个服务端同时执行中的请求。
- `-Dhnexam.loadtest.recover=true`：仅为继续诊断而顺序重试失败用户，保留初次错误。它不是应用提供的重试功能，存在初次失败时最终测试仍应失败。

MySQL 原始结果输出到 `backend/target/mysql-load-report.json`，重跑前需要自行留存。到期测试使用实体的 Instant 映射重置测试截止时间，避免 JDBC Timestamp 与 MySQL DATETIME 时区差异造成错误结论。整体计时不包含建库、种子数据及应用启动；突发读取的计时包含 HttpClient 内部连接排队。

本轮完整报告和各轮原始 JSON 位于 `E:/exam/2026-10-08/ji-xu/outputs`。正式部署前仍需修复问题，并在计划使用的服务器与独立压测机上复验。

## 本次修改

- 考试页面第一次定时上传随机分散在进入后的1～60秒，之后每60秒上传一次。2000份活动答卷的稳态自动保存平均约33次请求/秒。首次集中进入仍须单独压测。
- 每次修改仍即时尝试保存本机草稿；切屏、恢复网络、离开页面、交卷保持原有即时上传。没有修改也保留每分钟请求，用于获知取消/交卷状态。
- 断网草稿不能代替服务器确认：考试截止后仍执行既有规则，按最后成功同步的答案判分，不接收逾期答案。关闭/丢失设备可能丢失尚未上传的内容。
- 超时任务不再锁定所有在考答卷：只读筛选到期、已关闭考试以及兼容旧数据所需的空截止时间记录，按ID分批读取。未到期的旧记录只检查、不加锁。
- 每份到期答卷由独立事务处理，加锁后重新检查状态；已交卷时不重复判分。一份失败后继续其他答卷，后续扫描重试。
- 默认每批100份，每轮最多20批、5秒工作预算。预算在处理完单份后检查，不是强制中断；事务超时5秒，锁等待提示1秒的实际支持情况依数据库而定。任务每轮结束15秒后再次运行，游标保留进度。
- 沿用已有 `(status, deadline)` 索引；题目关联合并查询，配置批量读取64条；数据库连接池默认最多30条，等待连接上限由3秒调整为可配置10秒，吸收集中开考时的短时排队。未通过扩大连接池冒充吞吐提升。

## 复现

在后端目录使用Java 17运行：

```powershell
mvn test
mvn -Dhnexam.loadtest=true -Dtest=ExamHttpLoadTest test
```

第二条是显式开启的HTTP负载测试，平时回归默认跳过。测试使用独立H2内存数据库和随机HTTP端口，禁用本地配置文件导入、外部题库和Redis，不向正式库写入测试人员或答卷。报告生成在 `backend/target/http-load-report.json`。

### 测试场景

1. 预置2000名隔离考生、签发正常JWT；通过真实HTTP接口进入每份50道选择题的考试。
2. 保持2000份在考答卷，一分钟内错开2000次保存。
3. 集中提交2000份答卷，最多100个HTTP请求同时执行，超出的请求在负载端排队。
4. 通过HTTP逐份回读、核对全部10万条答案及预期分数，检查重复/遗漏。
5. 仅在测试库把这2000份答卷重置为到期在考状态，让真实定时任务完成交卷；检查2000份全部结束、分数正确、答案条数不变。

HTTP指标从实际发送到收到响应计时，不含负载端排队。预置JWT排除了密码校验成本；本次不是2000条请求同时冲击服务器，也不是2000个真实浏览器。

### 必须在正式上线前补测

- 拟用云服务器、MySQL、Redis、HTTPS反向代理及真实带宽；独立压测机避免客户端与服务端争抢资源。
- 真实试卷（含简答题/图片/不同长度答案）、真实数据规模和90分钟等完整考试时长。
- 集中密码登录、集中开考/截止提交、断网恢复、管理员操作、CPU/内存/磁盘/数据库锁监控。
- 以保存和交卷成功率、响应时间、逐条数据核对结果确定可承载人数；小规格试用服务器没有因此获得2000人容量保证。

## 可调整参数

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `HNEXAM_DB_POOL_MAX` | 30 | 数据库连接池上限；增加前检查数据库容量 |
| `HNEXAM_DB_POOL_MIN` | 5 | 最小空闲连接 |
| `HNEXAM_DB_CONNECTION_TIMEOUT_MS` | 10000 | 请求等待数据库连接的最长毫秒数 |
| `app.exams.expiry-check-ms` | 15000 | 到期任务轮次间隔 |
| `app.exams.expiry-batch-size` | 100 | 每批候选数量（代码限制最大500） |
| `app.exams.expiry-max-batches` | 20 | 单轮最多批次数 |
| `app.exams.expiry-run-budget-ms` | 5000 | 单轮处理预算，单份完成后检查 |

后台修改在重启后生效；前端刷新页面加载新版本。
